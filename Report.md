## 1. Executive Summary

AutoScoring is a web-based Final Year Project that helps instructors grade **subjective (long-answer) exam questions** using Natural Language Processing (NLP).

The system:

1. Accepts a **question paper** (upload) or a manually typed question.
2. Produces (or accepts) a **model/reference answer**, **marking rubric**, and **key concepts**.
3. Accepts a **student answer** as typed text or as a scanned/photographed paper.
4. Uses OCR where needed to extract text.
5. Scores the student answer against the model answer using a pretrained transformer embedding model (**MiniLM**).
6. Returns a numeric score plus a transparent breakdown and feedback.

**Important clarification for viva/supervisor:**

- The **scoring model (MiniLM) does not invent marks from thin air**.
- It **compares** the student answer with a **reference model answer**.
- In the **new architecture**, that reference can be **generated by an LLM** from the uploaded question paper, then **reviewed by the teacher** before scoring.

The project evolved in two major phases:

| Phase | Name | Core idea |
|-------|------|-----------|
| **V1 (Old)** | Manual reference scoring | Teacher types question + model answer; EasyOCR for student papers; MiniLM scores |
| **V2 (New)** | End-to-end paper pipeline | Upload question paper → OCR → LLM generates answer key/rubric/concepts → TrOCR for student handwriting → MiniLM scores |

Both flows still exist in the same codebase so we can compare them.

## 2. Problem Statement & Objectives

### 2.1 Problem statement

Subjective exams are essential for assessing understanding, but manual marking is:

- **Time-consuming** for large classes
- **Inconsistent** across markers and time
- **Difficult to scale** in university settings

Keyword-only systems fail because two correct answers can use different words. Modern NLP (transformers) can compare **meaning**, not only exact words.

### 2.2 Aims and objectives

1. Automate scoring of subjective answers using NLP / deep learning embeddings.
2. Support both **typed** answers and **written papers** (PDF/photo + OCR).
3. Provide an instructor dashboard to manage questions, view scores, and review feedback.
4. Make grading more **transparent** (score breakdown, matched/missing concepts).
5. Align with supervisor guidance: ingest a **question paper**, auto-generate **model answer + rubric + key concepts**, then grade student scripts.
6. Evaluate system scores against human teacher scores using appropriate metrics (not classification-only metrics).

### 2.3 Scope

**In scope**
- Instructor authentication and dashboard
- Question management (manual + paper upload pipeline)
- OCR for question papers and student papers
- LLM-assisted generation of model answers / rubrics / key concepts (optional API key)
- Hybrid semantic scoring (MiniLM + keywords + coherence)
- Evaluation script vs human marks
- Docker-based local deployment

**Out of scope (current version)**
- Fully unsupervised grading with no reference answer
- Objective MCQ grading
- Plagiarism detection as a primary feature
- Fine-tuning MiniLM on a large KIU-only labeled dataset (planned as future work)
- Guaranteed perfect handwriting recognition on all scripts

## 3. Problem Type (ML Perspective)

| Question | Our answer |
|----------|------------|
| What does the system output? | A **continuous / ordinal score** (e.g. 0–10) |
| Closest ML category | **Regression / Automated Essay Scoring (AES)** style agreement |
| Ground truth for evaluation | Human teacher marks |
| Is it classification? | **No** (unless we artificially band scores into Pass/Fail) |

### Why this matters for metrics

Precision, Recall, F1, and Accuracy assume **class labels** (True Positive, False Positive, etc.).

Our system predicts a **number**. Therefore primary metrics are:

- **Pearson correlation**
- **Spearman correlation**
- **Quadratic Weighted Kappa (QWK)**
- **MAE / RMSE**
- Agreement within ±1 / ±2 marks

Using only “accuracy = exact same mark as teacher” unfairly punishes near-misses (7.5 vs 8.0).

## 4. Software Development Life Cycle (SDLC)

We followed an **iterative / Agile-inspired SDLC**, not a single rigid waterfall pass. Because this is an FYP with evolving supervisor feedback, iteration was essential.

### 4.1 SDLC model chosen: Iterative Incremental Development

**Why not pure Waterfall?**
- Requirements changed after supervisor review (from manual model answers → auto-generated model paper pipeline).
- OCR/NLP components needed early prototypes to discover dependency and accuracy issues.
- Demoable increments were required for feedback.

**Why Iterative Incremental fits**
- Build a working core first (auth + scoring).
- Add OCR.
- Add paper pipeline + LLM generation + TrOCR.
- Keep older path available for comparison.

## 6. Technology Stack & Framework Choices

### 6.1 Stack summary

| Layer | Technology | Role |
|-------|------------|------|
| Frontend | React 18 + TypeScript + Vite | SPA instructor UI |
| UI styling | Tailwind CSS + Radix/shadcn-style components | Layout, forms, accessibility primitives |
| Backend | FastAPI (Python 3.11) + Uvicorn | REST API |
| ORM / DB | SQLAlchemy + PostgreSQL 16 | Persistence |
| Auth | JWT (python-jose) + passlib/bcrypt | Secure instructor sessions |
| Scoring NLP | `sentence-transformers/all-MiniLM-L6-v2` | Semantic embeddings |
| Similarity math | scikit-learn cosine similarity | Compare embeddings |
| Question OCR | EasyOCR | Printed question papers / general OCR |
| Student OCR | TrOCR (`microsoft/trocr-base-handwritten`) + EasyOCR line detection | Handwriting |
| PDF handling | PyMuPDF (`fitz`) | PDF → images |
| Generation | OpenAI-compatible LLM API (optional) | Model answer / rubric / concepts |
| Fallback generation | Heuristic extractor (no API key) | Drafts from OCR text |
| Containers | Docker Compose | Reproducible run |
| Repo | GitHub | Version control / sharing |

### 6.2 Why these frameworks / libraries (rationale)

#### Why FastAPI (not Flask / Django)

| Option | Why we did / didn’t choose it |
|--------|-------------------------------|
| **FastAPI** | Chosen. Modern async-capable API, automatic OpenAPI docs, Pydantic validation, excellent for ML service wrapping |
| Flask | Simpler but weaker built-in validation/docs; we needed structured schemas for scoring payloads |
| Django | Heavier; full MVC stack unnecessary when React is the frontend |

#### Why React + Vite (not plain HTML / Next.js)

| Option | Rationale |
|--------|-----------|
| **React + Vite** | Fast local DX, component model for dashboard forms, TypeScript support |
| Next.js | Useful for SSR/SEO; not needed for private instructor dashboard |
| Plain HTML/JS | Harder to maintain multi-page authenticated UI |

#### Why PostgreSQL

- Relational model fits Instructors / Questions / Submissions
- Reliable persistence for FYP demos
- Standard in academic and industry backends

#### Why MiniLM (`all-MiniLM-L6-v2`)

- BERT-family semantic embeddings without training from scratch
- Small enough for CPU Docker (~90MB class download)
- Good speed/quality tradeoff for short/medium answers
- Available via HuggingFace `sentence-transformers`

#### Why EasyOCR + TrOCR (not only one)

- **EasyOCR:** strong for printed text / full-page detection; used for question papers and as line detector
- **TrOCR:** purpose-built for handwritten text recognition (line-level); used for student scripts
- Vision LLMs (GPT-4V etc.) are strong but paid and not fully “local model ownership”

#### Why Docker Compose

- Reproducible environment (Python deps + Postgres + frontend build)
- Avoids “works on my machine” issues with torch/OCR stacks

#### Why optional LLM API (OpenAI-compatible / Groq)

- Supervisor required auto generation of model answers and rubrics
- OpenAI-compatible HTTP API keeps code flexible (Groq free tier possible)
- System still works **without** a key using heuristic drafts + teacher edit

### 6.3 What we did **not** use (and why)

| Technology | Why not (as primary) |
|------------|----------------------|
| Flask | FastAPI gives better schemas/docs for this API |
| Fine-tuned custom BERT classifier | Needs large labeled KIU dataset; not ready at prototype stage |
| PaddleOCR only | Supervisor suggested PaddleOCR in discussion; we implemented EasyOCR + TrOCR. PaddleOCR remains a possible swap for question OCR in future |
| GPT-4V as only OCR | Cost + external dependency; weaker for “models run in our stack” narrative |
| Classification F1 as main metric | Wrong problem type for continuous marks |

## 8. Drawbacks of the Old Architecture

These drawbacks became clear in supervisor discussions and practical use:

### 8.1 Heavy manual setup for teachers

For every question, the instructor had to **type the full model answer**.  
In real exams, teachers already have a **printed question paper**; they should not re-type everything.

### 8.2 No automatic answer-key generation

Supervisor expectation:

> Upload question paper → system should help generate model paper / rubric.

V1 could not do that. Without a reference, the system also cannot “know correctness” from the question alone.

### 8.3 No explicit marking rubric / key concepts fields

V1 mainly stored `model_answer`.  
Rubric and key concepts were implicit (derived from model answer text during scoring), not first-class generated artifacts.

### 8.4 EasyOCR limitations on handwriting

EasyOCR is convenient for full pages and print, but handwriting quality varies.  
Supervisor discussion highlighted **TrOCR** as more purpose-built for handwritten recognition (with line segmentation).

### 8.5 Incomplete end-to-end exam workflow

V1 was strong as a **scoring engine**, but incomplete as a full **exam processing pipeline**:

- Question paper ingest ❌
- Auto extract questions ❌
- Auto model answers / rubric ❌
- Handwriting-specialized OCR ❌

### 8.6 Communication risk (important)

Because V1 was demoable, it could be mistaken as the final architecture.  
Supervisor feedback clarified that the intended FYP vision is the **paper → generate key → grade student** pipeline.

## 9. New Architecture (Version 2 — Supervisor-Aligned)

### 9.1 Design goal of V2

Implement the supervisor’s end-to-end flow while keeping teacher control:

1. Upload question paper  
2. OCR  
3. Extract questions  
4. AI generates model answer + marking rubric + key concepts  
5. Teacher reviews/edits  
6. Student uploads answer  
7. TrOCR  
8. Scoring service  
9. Marks + feedback  

### 9.2 V2 pipeline diagram

```
Teacher uploads Question Paper (PDF/Image)
                │
                ▼
         EasyOCR (question paper)
                │
                ▼
         Extract Questions
                │
                ▼
         AI / LLM Generation
         ┌─────────────────────┐
         │ Model Answer        │
         │ Marking Rubric      │
         │ Key Concepts        │
         └─────────────────────┘
                │
                ▼
     Teacher Review / Edit / Save
                │
                ▼
 Student uploads Answer Sheet
                │
                ▼
     TrOCR (handwriting lines)
                │
                ▼
         Student Answer Text
                │
                ▼
         Scoring Service (MiniLM)
         (+ key-concept-aware keywords)
                │
                ▼
         Marks + Detailed Feedback
```

### 9.3 Safety design: teacher-in-the-loop

LLM-generated answer keys can be wrong.  
Therefore V2 **requires review** before trust:

- Generated drafts are editable in UI
- Without `LLM_API_KEY`, heuristic drafts are produced and clearly warned
- Final stored model answer is what scoring uses

This preserves fairness better than blind auto-marking against unverified AI keys.

### 9.4 Dual path retained

| Path | Entry point | Use |
|------|-------------|-----|
| Old | Questions → New question | Manual reference scoring |
| New | Upload paper | Supervisor architecture |

This allows side-by-side comparison for report/viva.

## 10. Why We Changed / Why We Chose the New Architecture

### 10.1 Supervisor requirement

The supervisor specified an architecture where the system:

- Reads the **question paper**
- Automatically generates a **model paper** (answer + rubric + concepts)
- Compares with the **student paper**

Continuing only with V1 would misalign with assessed FYP expectations.

### 10.2 Closer to real exam operations

Real workflow is paper-centric:

1. Exam paper exists
2. Students write answers
3. Teachers mark against a key/rubric

V2 mirrors that more closely than “type everything into forms.”

### 10.3 Better research narrative

V2 combines multiple AI components:

- Document OCR
- Information extraction
- Generative LLM for answer keys
- Handwriting OCR (TrOCR)
- Semantic scoring (MiniLM)

This is richer for methodology chapters than similarity alone.

### 10.4 Why not abandon MiniLM scoring?

Because generation and scoring solve **different problems**:

| Component | Job |
|-----------|-----|
| LLM | Create/draft the reference answer & rubric from the question |
| MiniLM scoring | Measure similarity/coverage of student response vs reference |

Replacing scoring with “ask LLM to give marks” is possible, but:

- harder to control consistency
- harder to evaluate with classic AES metrics
- more expensive per submission

So V2 **extends** V1’s scoring core rather than deleting it.

### 10.5 Why teacher review remains

Without review, a wrong generated model answer would systematically mis-score an entire class.  
Teacher-in-the-loop is both an ethical and engineering decision.

## 12. How Scoring Works (Core NLP Engine)

### 12.1 Model used

**Name:** `sentence-transformers/all-MiniLM-L6-v2`  

**Where configured:** `backend/app/config.py`  
**Where loaded:** `backend/app/services/scoring.py` via `SentenceTransformer(...)`  

**Nature:** Pretrained embedding model (inference). Not trained from scratch in this FYP.  
**Weights location:** HuggingFace cache (not committed in Git). Docker volume `model_cache` persists downloads.

### 12.2 Does the model “score by itself”?

**No.**

It does **not** generate its own secret answer key during scoring.  
It embeds:

- teacher/LLM-approved **model answer**
- **student answer**

then computes similarity and supporting features.

### 12.3 Formula

\[
\text{weighted} = 0.60\cdot\text{semantic} + 0.25\cdot\text{keywords} + 0.15\cdot\text{coherence}
\]

\[
\text{final score} = \text{weighted} \times \text{max\_score}
\]

Weights are configurable in settings (`weight_semantic`, `weight_keywords`, `weight_coherence`).

### 12.4 Feature meanings

| Feature | Meaning |
|---------|---------|
| Semantic similarity | Cosine similarity of MiniLM embeddings |
| Keyword coverage | Overlap of important terms; prefers explicit `key_concepts` when present |
| Coherence | Heuristic on length, sentence structure, repetition |

### 12.5 Detailed report outputs

- Matched / partial / missing concepts
- Matched / missing keywords
- Strengths / weaknesses
- Optional OCR quality note

## 13. OCR Strategy (EasyOCR vs TrOCR)

### 13.1 Question papers → EasyOCR

Printed exam papers are usually clearer layout/print.  
EasyOCR detects text regions across a full page well enough for question extraction.

Configured as `question_ocr_engine = easyocr`.

### 13.2 Student handwriting → TrOCR

TrOCR (`microsoft/trocr-base-handwritten`) is designed for handwritten line recognition.  
It typically needs **line crops**, not a full messy page at once.

Our approach:

1. EasyOCR detects line/word boxes  
2. Each crop is passed to TrOCR  
3. If TrOCR fails to load, fallback to EasyOCR text

Configured as `student_ocr_engine = trocr`.

### 13.3 Why not only GPT-4V / Claude vision?

- Paid APIs
- Less “local stack” ownership for FYP engineering story
- Still useful as future enhancement

## 14. LLM Generation Layer

### 14.1 Role

After question-paper OCR, generation service produces drafts:

- `question_text`
- `model_answer`
- `marking_rubric`
- `key_concepts`
- `max_score` (from paper marks when detected)

### 14.2 Modes

| Mode | When | Behavior |
|------|------|----------|
| **LLM mode** | `LLM_API_KEY` set | Calls OpenAI-compatible Chat Completions API; parses JSON questions |
| **Heuristic mode** | No key / LLM failure | Splits OCR by numbered questions; drafts answer/rubric from extracted terms + warning |

### 14.3 Free vs paid keys

| Provider | Typical cost |
|----------|--------------|
| No key | Free; drafts need editing |
| Groq free tier | Often free with limits |
| OpenAI | Paid (usage-based) |

TrOCR/MiniLM/EasyOCR themselves do **not** require paid keys.

### 14.4 Code location

`backend/app/services/generation.py`

## 19. Evaluation Methodology & Metrics

### 19.1 Purpose of `evaluation.py` / `evaluate.py`

These modules **do not grade students in production UI**.  
They measure how well AutoScoring agrees with **human teacher marks** on a labeled CSV.

### 19.2 Metrics we use (and why)

| Metric | Advantage | Drawback |
|--------|-----------|----------|
| Pearson r | Standard linear association | Outlier-sensitive |
| Spearman ρ | Rank agreement; robust to monotone scaling | Ignores absolute error size |
| QWK | AES standard; penalizes large disagreements more | Needs discretization/rounding |
| MAE | Interpretable average points off | Treats all errors linearly |
| RMSE | Punishes large mistakes more | Less intuitive |
| R² | Variance explained | Can look good despite bias |
| Within ±1/±2 | Practical teacher tolerance | Thresholds arbitrary |
| Exact match | Strict upper bound | Too harsh alone |

### 19.3 Metrics that are usually wrong as primary here

| Metric | Why not primary |
|--------|-----------------|
| Accuracy / F1 / Precision / Recall | Classification metrics; need labels |
| Simple average equality | Means can match while individuals are wrong |
| ROI / industrial KPIs | Not applicable to NLP scoring task |

### 19.4 Current evaluation limitation (honest)

Sample CSV is small/synthetic.  
Final academic claims need a larger real teacher-scored dataset and hyperparameter tables.

## 24. Conclusion

AutoScoring began as a **reference-based MiniLM scoring system** with manual model answers and EasyOCR (Architecture V1).  
That version was useful and correct as a scoring engine, but incomplete as a full exam-paper workflow.

After supervisor guidance, we extended the system to Architecture V2:

**Question paper upload → OCR → extract questions → generate model answer/rubric/key concepts → teacher review → student TrOCR → MiniLM scoring → marks/feedback.**

We chose this new architecture because it:

- matches supervisor expectations,
- mirrors real exam operations,
- expands the AI pipeline for a stronger FYP narrative,
- while preserving the reliable MiniLM comparison core and teacher control.

The old path remains available for comparison, demonstrating that the change was an **intentional architectural evolution**, not a random rewrite.
